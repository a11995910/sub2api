# 上游 v0.1.182 同步与发布 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 将固定的 `upstream/main` 提交 `832cf4df659acc0a0d45feccb2b7bf99ea606198` 三方合并到定制仓库，在保留定制图片、视频计费和发布门禁的前提下吸收 v0.1.182 修复，并把同一 `main` commit 依次发布到隔离 staging 和 prod。

**架构：** 以干净的本地 `main` 和 `origin/main` 提交 `dc978e4ca431b448e7565894f60b23238bb20a1d` 为合并基线，生成具有双方父提交的普通 merge commit。两个内容冲突按“组合双方语义”解决；本地验证通过后重新确认上游目标和 origin 基线未变化，再普通推送 `main`。正式 VPS 只拉取该 commit，并通过仓库受控脚本完成 staging、异机备份凭证校验、prod 切换和失败回滚。

**技术栈：** Git、Go、Gin、Vue 3、TypeScript、Vitest、Docker Buildx、Docker Compose、PostgreSQL 18、Redis、Bash。

## 全局约束

- 全程使用中文报告；不得打印、持久化或写入仓库任何服务器、数据库、Token、Cookie 或 SSH 凭据。
- 本地和正式 VPS 的发布来源都只能是 `origin/main`，禁止 force push，merge commit 必须保留定制分支与上游的两个父提交。
- 目标上游必须保持为 `832cf4df659acc0a0d45feccb2b7bf99ea606198`；推送前重新抓取发现 SHA 变化时停止并重新审查新增差异。
- 合并基线必须保持为 `dc978e4ca431b448e7565894f60b23238bb20a1d`；推送前发现 `origin/main` 变化时停止，不覆盖他人提交。
- 正式 VPS 构建使用 `deploy/Dockerfile`、带 commit 的镜像 tag 和 `GOMAXPROCS=2`；staging 与 prod 使用独立 compose project、数据库、Redis、目录和端口。
- prod 只能使用同一 commit 的 verified staging 结果和两小时内的异机全库备份凭证；任一门禁失败即停止切换。
- 异机归档只能落在备份机 `/opt/sub2api-prod-backup/archives`，正式 VPS 和本机不得保存 prod 全库 dump。
- 发布失败时保留现场并由 `deploy/release-prod` 恢复原正式镜像；恢复后的 Docker health 和宿主机 HTTP 必须同时通过。

```go
func (s *BillingService) computeCacheCreationCost(pricing *ModelPricing, tokens UsageTokens, price, multiplier float64) float64 {
	if pricing.SupportsCacheBreakdown && (pricing.CacheCreation5mPrice > 0 || pricing.CacheCreation1hPrice > 0) {
		cacheCreation5mTokens, cacheCreation1hTokens := normalizeCacheCreationBreakdown(tokens)
		if cacheCreation5mTokens == 0 && cacheCreation1hTokens == 0 && tokens.CacheCreationTokens > 0 {
			return float64(tokens.CacheCreationTokens) * pricing.CacheCreation5mPrice * multiplier
		}
		return float64(cacheCreation5mTokens)*pricing.CacheCreation5mPrice*multiplier +
			float64(cacheCreation1hTokens)*pricing.CacheCreation1hPrice*multiplier
	}
	return float64(tokens.CacheCreationTokens) * price * multiplier
}
```

### 任务 6：生成并校验异机全库备份凭证

**文件：**
- 运行时：备份机 `/opt/sub2api-prod-backup/archives/sub2api-prod-<UTC时间>.dump.zst`
- 运行时：正式 VPS `/opt/sub2api/state/prod-backup-result.json`

**接口：**
- 消费：目标完整 commit、任务 5 的 staging run ID、当前 prod PostgreSQL
- 产出：SHA-256、zstd 和 PostgreSQL 18 `pg_restore --list` 均通过的两小时内 root-only 凭证

- [ ] **步骤 1：使用运行时 SSH 凭据流式生成异机归档**

从本机建立到两台主机的加密管道，归档只写入备份机：

```bash
archive="sub2api-prod-$(date -u +%Y%m%dT%H%M%SZ).dump.zst"
set -o pipefail
ssh sub2api-new-vps \
  "docker exec -i sub2api-prod-postgres sh -c 'pg_dump -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" -Fc'" \
  | ssh root@192.220.36.75 "umask 077; zstd -q -T1 -o /opt/sub2api-prod-backup/archives/$archive"
```

预期：管道退出码为 0，本机和正式 VPS 均未生成全库 dump。SSH 凭据只允许运行时输入，不得出现在命令历史、日志或仓库。

- [ ] **步骤 2：在备份机独立校验归档**

运行：

```bash
ssh root@192.220.36.75 "bash -s -- '$archive'" <<'REMOTE'
set -Eeuo pipefail
archive="/opt/sub2api-prod-backup/archives/$1"
test -s "$archive"
sha256sum "$archive" > "$archive.sha256"
zstd -q -t "$archive"
toc="$(mktemp /tmp/sub2api-prod-backup-toc.XXXXXX)"
trap 'rm -f -- "$toc"' EXIT
zstd -q -dc "$archive" | docker run --rm -i postgres:18-alpine pg_restore --list > "$toc"
test "$(awk '!/^;/ && NF {count++} END {print count + 0}' "$toc")" -ge 100
REMOTE
```

预期：归档非空，SHA-256、zstd 和 TOC 至少 100 项全部通过。

- [ ] **步骤 3：写入并校验最小备份凭证**

凭证字段严格限定为文档约定的十一个非敏感字段，`target_commit` 和 `staging_run_id` 来自任务 5，`verified_at` 使用当前 UTC ISO 8601 时间。写入后执行：

```bash
chown root:root /opt/sub2api/state/prod-backup-result.json
chmod 0600 /opt/sub2api/state/prod-backup-result.json
/opt/sub2api/repo/deploy/release-gates validate-backup-receipt \
  /opt/sub2api/state/prod-backup-result.json "$target_commit" "$staging_run_id"
```

预期：权限为 `root:root 600`，commit、run ID、时间、大小、SHA、zstd 和 TOC 字段全部通过门禁。
