# 抽奖功能

抽奖是 Sub2API 的内置功能，由宿主负责用户身份、用量核算、机会账本、余额入账、
流水记录和数据库事务。该功能涉及用户用量与资金一致性，不通过外部插件进程实现。

## 业务规则

- `1M` 等于 `1,000,000 Token`；
- 每日用量为输入、输出、缓存创建和缓存读取 Token 之和；
- 机会发放支持“每天最多一次”和“每达到门槛一次”两种模式；
- 按门槛模式使用 `floor(当天用量 / 门槛)` 计算当天应得次数；
- 当天修改门槛或模式时只补发新增次数，不追回已经发放的机会；
- 抽奖机会永久累计，不按自然日或自然月清零；
- 最多配置 5 个余额奖项，单个奖项概率精确到 `0.01%`；
- 奖励余额按数据库金额精度统一到 8 位小数；
- 奖项概率总和不能超过 `100%`；
- “谢谢惠顾”固定存在且不可删除，概率为其他奖项概率之和的剩余值；
- 没有余额奖项时，“谢谢惠顾”为 `100%`。

例如门槛为 `1M`，用户当天使用 `3.4M`：每天最多一次模式发放 1 次；每达到
门槛一次模式发放 3 次，并继续显示到 `4M` 的进度。第二天从新的当日用量开始
计算，但前一天尚未抽取的机会继续保留。

## 安全与一致性

中奖随机数由服务端 `crypto/rand` 生成，浏览器只根据服务端返回结果播放动画。
同一用户的机会核算通过数据库事务和行锁串行化；每日账本只追加应得次数的差额，
重复请求或并发请求不会重复发放。

每次抽奖在同一事务内完成：

1. 锁定用户机会状态；
2. 扣减一次机会；
3. 增加中奖余额；
4. 写入抽奖流水；
5. 提交后失效 API Key 鉴权余额缓存和计费余额缓存。

任一步失败都会回滚整次抽奖。抽奖奖励属于活动赠送，不计入累计充值金额。

## 配置与版本

总开关是系统设置 `lottery_enabled`，管理入口位于“系统设置 → 功能开关”。门槛、
发放模式和奖项在“抽奖管理”配置。总开关保存时会在同一数据库事务内同步抽奖
运行快照和当天规则版本，避免设置值与实际运行状态分叉。

全局规则和奖项保存在 `sub2api_lottery_settings`。门槛、启用状态和发放模式按自然日
写入 `sub2api_lottery_rule_versions`，后续修改配置不会用新规则重算已经结束的日期。
关闭功能不会清空已经获得的机会或历史流水。

`sub2api_lottery_daily_awards` 保存用户每天已经发放的次数；
`sub2api_lottery_user_states` 保存可用、累计获得和累计抽取次数；
`sub2api_lottery_draws` 是余额奖励与机会变化的抽奖流水。

## 接口

用户接口：

- `GET /api/v1/lottery`：核算机会并返回配置、当日进度和最近流水；
- `POST /api/v1/lottery/draw`：消费一次机会并返回服务端抽奖结果。

管理员接口：

- `GET /api/v1/admin/lottery/config`：读取配置；
- `PUT /api/v1/admin/lottery/config`：保存配置，需要二次验证；
- `GET /api/v1/admin/lottery/draws`：分页读取抽奖流水。

## 构建与发布

抽奖规则、服务和数据访问代码位于后端 `internal` 包，前端页面位于用户端与管理端
视图目录，随 Sub2API 主镜像一起构建和发布。

本地验证至少执行：

```bash
cd backend
go test ./internal/service ./internal/repository ./migrations ./cmd/server

cd ../frontend
pnpm typecheck
pnpm test:run
pnpm build
```

生产发布仍遵守仓库的 staging、同 commit 验证、异机备份和明确口头确认门禁。
